## 1. 版本定位与范围

### 1.1 版本定位

继续候选版序列，目标版本 `v0.3.0`。D 功能（工作流改进）作为本版核心内容；
A 门槛（法律复核 / 代码签名 / Inno Setup 商用许可）作为 v0.3.0 周期内的并行
准备项，不阻塞 D 功能开发，但阻塞正式版发布。

### 1.2 范围

本版包含 7 项子 spec：

| 序号 | 子 spec | 类型 |
|---|---|---|
| 1 | 监视文件夹（watch folder） | D 功能 |
| 2 | 批量后处理（重命名 / 水印 / EXIF） | D 功能 |
| 3 | 项目/客户预设与归档 | D 功能 |
| 4 | 历史搜索与前后对比 | D 功能 |
| 5 | UI 升级 A：视觉语言与设计系统 | UI |
| 6 | UI 升级 B：信息架构与交互模式 | UI |
| 7 | UI 升级 C：响应性与可访问性收口 | UI |

### 1.3 明确不做（YAGNI）

以下内容不纳入 v0.3.0，留给后续版本：

- GPU 推理路径（CUDA EP / DirectML EP），留给 v0.4
- RAW 原生支持（CR3 / NEF / ARW / DNG），留给 v0.4+
- 港澳台及国际车牌，留给 v0.4+
- 视频批量处理，留给 v0.4+
- SD inpainting 作为高级精修模式，留给 v0.4+
- 模型微调，不在本周期
- 自动更新通道，不在本周期
- OCR（产品定位不执行 OCR）

### 1.4 A 门槛并行准备项

以下项目不在本 spec 实现代码，仅作为 v0.3.0 周期内的并行任务记录：

- Paddle 权重再分发法律复核材料准备

## 2. 子 Spec 拆解

### 2.1 子 spec 1：监视文件夹

**目标**：拖入文件夹时可勾选"开启监视"，新增照片自动入批；
可在设置中管理多个监视文件夹。监视功能默认关闭，用户显式开启。

**核心组件**：

- `WatchFolderService`（独立线程，基于 `ReadDirectoryChangesW`，避免轮询开销）
- 与 `BatchService` 复用 start / pause / resume / cancel
- 设置页新增"监视文件夹"管理区

**数据模型影响**：

- `settings.json` 新增 `watch_folders: [{path, enabled, preset_id}]`
- `jobs.sqlite3` 无需改 schema（监视入队的任务与普通任务同构）

**测试边界**：

- `WatchFolderService` 单元测试（模拟文件创建事件）
- 集成测试：真实文件夹新增照片 → 自动入队
- 边界：监视开启时文件夹被删除 / 移动 / 重命名

### 2.2 子 spec 2：批量后处理

**目标**：处理完成后按模板自动重命名、叠加水印、填写 EXIF 字段。

**核心组件**：

- `PostProcessor`（处理完成钩子）
- `NamingTemplate`（解析 `{client}_{seq:03}_{date}.{ext}` 等模板）
- `WatermarkRenderer`（基于 OpenCV / Pillow 渲染文字 / 图片水印）
- `ExifWriter`（基于已有 `piexif`，填入 IPTC / EXIF 字段）

**数据模型影响**：

- `settings.json` 新增 `post_process_config: {naming_template, watermark, exif_fields}`
- `jobs.sqlite3` 新增 `post_processed_output` 列（区分原始输出与后处理输出）

**测试边界**：

- `NamingTemplate` 解析单元测试（含中文 / 特殊字符 / 序列号冲突）
- `WatermarkRenderer` 渲染测试（位置 / 透明度 / 字体回退）
- `ExifWriter` 元数据保留测试（不破坏既有 EXIF）
- 集成测试：完整处理 → 后处理 → 输出验证

### 2.3 子 spec 3：项目/客户预设与归档

**目标**：按客户/项目保存预设（阈值 / 边缘 / 输出命名 / 水印），
切换客户时一键套用。

**核心组件**：

- `ProjectStore`（SQLite 表，与 `jobs.sqlite3` 同库）
- `ProjectPreset`（dataclass，含处理参数 + 后处理配置 + 输出目录规则）
- 批处理页顶部新增"当前项目"选择器

**数据模型影响**：

- `jobs.sqlite3` 新增 `projects` 表（id, name, preset_json, created_at, last_used_at）
- `jobs` 表新增 `project_id` 外键（可空，兼容旧任务）

**测试边界**：

- `ProjectStore` CRUD 测试
- 预设套用集成测试（切换项目 → 参数生效）
- 兼容性测试（无 project_id 的旧任务正常显示）

### 2.4 子 spec 4：历史搜索与前后对比

**目标**：任务历史支持搜索 / 筛选 / 按项目分组；
原图与结果并排对比（替代当前 tab 切换）。

**核心组件**：

- `HistorySearchService`（按状态 / 日期 / 名称 / 项目查询）
- 前端 `ComparisonView` 组件（左右并排 + 滑块对比 + 差分高亮）
- 前端筛选侧边栏

**数据模型影响**：

- `jobs.sqlite3` 无新表，可能为 `projects` 关联加索引
- 后端 `list_history` 增加 `query` 参数

**测试边界**：

- `HistorySearchService` 查询测试（各筛选组合）
- `ComparisonView` 前端组件测试（并排渲染 + 滑块交互）
- 性能测试（500+ 任务列表渲染）

### 2.5 子 spec 5：UI 升级 A — 视觉语言与设计系统

**目标**：定义 v0.3.0 的视觉语言，更新设计系统，
为后续 UI 子 spec 与四个 D 功能的视觉表达定调。

**核心组件**：

- `design-system/MASTER.md` 更新（新组件、新动效规范、新 token）
- 组件库扩展：项目选择器、对比视图、筛选条、向导弹出、监视文件夹管理区
- 视觉精进：排版细节、微动效、高端商务感

**数据模型影响**：无（纯前端 + 文档）

**测试边界**：

- 视觉证据：`docs/audits/v0.3.0/` 截图
- 设计 token 一致性检查

### 2.6 子 spec 6：UI 升级 B — 信息架构与交互模式

**目标**：重构导航与新功能入口布局，定义动效系统与交互反馈。

**核心组件**：

- 导航重构（四个 D 功能的入口归位）
- 动效系统（150-220ms 过渡，遵守 `prefers-reduced-motion`）
- 交互反馈：处理进度可视化、拖拽反馈、快捷键提示、错误状态

**数据模型影响**：无（纯前端）

**测试边界**：

- 前端组件单元测试
- 交互流程验证（键盘 / 鼠标 / 触摸板）

### 2.7 子 spec 7：UI 升级 C — 响应性与可访问性收口

**目标**：多分辨率适配、高 DPI、窄窗口、键盘导航、ARIA 全面审查与修复。

**核心组件**：

- 响应式断点规范（1040×680 / 1280×820 / 1920×1080 三档）
- 高 DPI 资源（图标 / 字体）
- 键盘导航完整性
- ARIA 角色与标签审查
- `prefers-reduced-motion` / `prefers-contrast` 支持

**数据模型影响**：无

**测试边界**：

- 三档分辨率视觉回归
- 键盘导航完整性测试
- 可访问性审查（屏幕阅读器友好）

## 3. 横切关注点

所有 7 个子 spec 都必须遵守以下共同约束。

### 3.1 数据模型一致性

- 所有 schema 变更集中在 `app/core/job_store.py`，schema_version 从 4 升到 5
- 迁移必须保持兼容：无 `project_id` 的旧任务、无 `post_processed_output` 的旧记录、
  无 `watch_folder` 配置的旧 settings 都能正常运行
- 每个子 spec 只定义自己新增的字段 / 表，总纲 spec 记录最终 schema 全貌

### 3.2 后端桥接扩展规则

延续 `app/desktop.py` 的白名单 API 模式：

- 新增方法只暴露任务 ID、项目 ID、配置对象，**不接收任意文件路径**
- 监视文件夹路径通过设置存储，前端只传 `watch_folder_id`
- 批量后处理模板通过 `post_process_config` 对象传递，前端不直接拼接命令

### 3.3 前端架构扩展规则

延续 `app/web/` 无框架、无 CDN、CSP `connect-src 'none'` 约束：

- 新组件放入 `app/web/components/`，遵循 `dialog.js` / `toast.js` 的模块模式
- 新页面或子区域放入对应 workspace 目录（如 `app/web/projects/`）
- 状态管理扩展 `app/web/core/state.js` 的 store 模式，不引入新状态库

### 3.4 测试策略

每个子 spec 必须包含：

- Python 单元测试（`tests/unit/`）
- 前端测试（`tests/frontend/*.test.cjs`，延续 `node --test` 模式）
- 至少一个集成测试（`tests/integration/`，若涉及真实模型则加
  `@pytest.mark.model`）
- 视觉证据（UI 子 spec 需在 `docs/audits/v0.3.0/` 留截图）

### 3.5 文档同步规则

每个子 spec 完成后必须更新：

- `docs/user-guide.md`（用户视角）
- `docs/troubleshooting.md`（新增故障场景）
- `docs/privacy.md`（若涉及新数据存储）
- `docs/release-checklist.md`（累积本版证据）
- `RELEASE.md`（最终发布说明）

### 3.6 性能预算

- 监视文件夹：新增照片入队延迟 ≤ 2 秒
- 批量后处理：单图后处理增量 ≤ 500ms
- 历史搜索：500 任务查询 ≤ 200ms
- UI 升级：保留当前 P50 2.38 秒的推理性能基线，不因 UI 改动引入卡顿

### 3.7 隐私与离线约束

- 监视文件夹路径不写入诊断包（延续 `docs/privacy.md` 的路径保护）
- 项目 / 客户名称视为敏感信息，诊断包只统计数量不导出名称
- 批量后处理的水印图片不写入永久缓存，处理完即删
- 全部新功能不引入任何网络请求

## 4. 推进路线与里程碑

### 4.1 子 spec 推进顺序

按依赖关系排序，每个子 spec 走完整 brainstorm → spec → plan → 实现循环：

| 顺序 | 子 spec | 依赖 | 预估工作量 |
|---|---|---|---|
| 1 | 监视文件夹 | 无（依赖已有 BatchService） | 中 |
| 2 | 批量后处理 | 子 spec 1 的"输出后钩子"概念 | 大 |
| 3 | 项目/客户预设与归档 | 子 spec 2 的命名模板 | 中 |
| 4 | 历史搜索与前后对比 | 子 spec 3 的项目维度 | 中 |
| 5 | UI 升级 A：视觉语言与设计系统 | 子 spec 1-4 已定信息架构 | 大 |
| 6 | UI 升级 B：信息架构与交互模式 | 子 spec 5 的视觉规范 | 大 |
| 7 | UI 升级 C：响应性与可访问性收口 | 子 spec 5、6 完成 | 中 |

**关键依赖说明**：

- 子 spec 1-4 是功能层，相互之间弱耦合，可在实现阶段并行
- 子 spec 5-7 是 UI 层，强依赖前四项的信息架构已稳定
- 子 spec 5 → 6 → 7 严格串行（视觉 → 交互 → 收口）

### 4.2 里程碑

| 里程碑 | 内容 | 退出条件 |
|---|---|---|
| **M6** | v0.3.0 工程基线 + 7 份子 spec 完成 | 7 份 spec 文档 review 通过 |
| **M7** | 子 spec 1-4 实现 + 测试 | 四项功能单测 / 集成测试通过，可交付摄影师试用 |
| **M8** | 子 spec 5-7 实现 + 测试 | UI 升级完成，视觉 / 交互 / 可访问性审查通过 |
| **M9** | v0.3.0 候选版打包 | 全量测试通过，`dist/preview` 免安装版交付摄影师 |
| **M10** | A 门槛并行准备 | 法律材料 / 签名证书 / Inno 许可准备就绪（不阻塞 M9） |

### 4.3 版本号策略

- 开发期间：`v0.3.0-dev`（`pyproject.toml`）
- 候选版：`v0.3.0-rc.1` → `v0.3.0-rc.N`（每轮内部 review 后递增）
- 正式版：`v0.3.0`（仅在 M9 + A 门槛全部关闭后发布）

### 4.4 回归与质量门

每个子 spec 实现完成后必须通过：

- 全量单元测试（延续当前 141 passed 基线，只增不减）
- 前端测试（延续 `node --test` 模式）
- Ruff + 严格 mypy
- 桌面 smoke 测试（`python run.py --smoke`）
- 至少一次真实样片处理验证

### 4.5 风险与缓解

| 风险 | 缓解措施 |
|---|---|
| 范围过大导致 v0.3.0 周期拉长 | 每个子 spec 独立交付，可在某个 rc 提前交付部分功能 |
| 监视文件夹在 Windows 上的稳定性 | 使用 `ReadDirectoryChangesW`，避免轮询；含错误恢复 |
| 批量后处理的 EXIF 写入破坏既有元数据 | 复用已有 `_save_options` 路径，强制原子写入 + verify |
| UI 升级引入性能回退 | 子 spec 5-7 必须保留 P50 2.38s 推理基线 |
| A 门槛外部采购周期不可控 | A 门槛不阻塞 M9 候选版交付，只阻塞正式版发布 |
